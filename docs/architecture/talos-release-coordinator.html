System boundary

One source, two image paths

base + libvirt/QEMU · standard

There are two release paths after the shared version check. Unraid uses the base Talos image plus the -libvirt variant and libvirt/QEMU provider settings. OCI uses the standard installer and the OCI disk artifact. A pin to an already-built version runs reconcile.yml; a missing version stops there until talos-images builds the artifacts and writes the machine-owned ledger.

Relationship rules
VersionPin 1→N BuildRun: retries and extension changes can create multiple runs, but only a successful run can produce a ledger. BuildRun 1→1 TalosImageLedger: the image build is the single writer of schematic IDs, OCIDs, and extension metadata. Ledger → derived state: CI checks that rendered machine classes match intent. Unraid is not yet a downstream PR: its renderer requires an explicit --talos-version CLI input.
Plain explanation. These are not all database tables. Only the files named above are repository records. The other cards are labels for things that happen during the flow: choose a version, build images, record the result, and place the right image reference in each platform’s configuration.

New-version failure

The source pin is not treated as a request to build an unknown tag. The drift checker stops before writing nonexistent references. A dispatch to talos-images with an explicit version builds the missing artifact; the version is then pinned in the GitOps source.

Consumer boundary

OCI derived state is checked by GitOps CI. Unraid is a separate repository and currently requires the resolved version to be passed to its renderer through the CLI. Automating that edge is a future coordinator seam.

Plain explanation. The important stop is before configuration is written. A missing image is not silently treated as present. That leaves the version unchanged until a build has produced the required artifact. The OCI path is checked automatically; the Unraid path still needs its version supplied to the renderer.
Recovery boundary

Attempt correlation, not permanent claims

target design · unverified

The current release path has an observed recovery gap: a receiver can persist a duplicate-prevention claim before mutation, while the controller records a provider dispatch as sent only when it accepts a callback. An interrupted execution or lost callback can therefore leave the release pending even though replay is refused. A duplicate response is evidence that a claim exists—not evidence that mutation never happened, nor that the release has reached a terminal state.

Status and evidence
Verified current behavior (2026-09-05): omni-on-unraid/.github/workflows/release-dispatch.yml persists a claim before mutation and rejects cache-hit replay; talos-release-controller/release/coordinator.py marks a provider dispatch sent on accepted callback. Revalidate OCI receiver behavior from remote main before implementation.
Canonical open task: Recover Talos release dispatches with durable attempt correlation, a child of Wayfinder: Talos v1.14.0 release through versions.yaml.
Supporting record: syscode-ai-internal-plans/docs/research/2026-09-05-talos-release-recovery-findings.md. These findings are diagnosis and proposed acceptance criteria, not implementation or cluster-health proof.
01 / DURABLE IDENTITY
Keep the accepted releasePreserve approved source SHA, release ID, accepted build run, and exact immutable artifacts.
02 / ATTEMPT EVIDENCE
Correlate an attemptAssociate each provider attempt with authenticated workflow/run evidence; a receiver claim is not that correlation.
03 / OBSERVE
Running is non-mutatingObserve a correlated active run. Do not dispatch a competing destructive mutation.
04 / RECOVER ONCE
Finished has a resultRecover the authentic terminal result once. Retry only when failure before mutation is proven.
05 / FAIL CLOSED
Uncertain is blockedRecord a concrete inspection-required outcome; never silently hang or delete a claim to force progress.

Current defect — verified

  • Claim-before-mutation plus replay refusal protects against repeat destruction, but does not itself provide recovery.
  • Missing callback is not proof that execution never happened.
  • A successful replay workflow is not proof of release progress.

Target recovery semantics — proposed

  • Use bounded, durable attempt/run correlation and authenticated evidence.
  • Preserve success during partial provider failure; consider recovery only for unfinished work.
  • Recover completed builds/deployments without rebuilding or mutation when their callbacks were lost.
Acceptance remains open. The linked task must demonstrate lost build callback with zero rebuilds; claim-before-child interruption; duplicate delivery while original execution is running; lost deployment callback; partial success; and an explicit blocked uncertain-mutation outcome. It also retains the settled boundary: native github-runner.service, explicitly approved Docker group, service-account-only automation, source-PR merge as the sole approval, no same-host SSH/root wrapper, no local Terraform/OpenTofu, and existing OCI exact-plan/Always-Free gates.
Plain explanation. A “duplicate” answer says only that the receiver has seen this release. Recovery first finds the real correlated run, then observes it or applies its authenticated result. If nobody can prove what was mutated, the release stops visibly for inspection rather than guessing.

Dispatch trigger implemented in talos-images
talos-images/.github/workflows/build.yml declares repository_dispatch with type firecracker-release. It reads github.event.client_payload.talos_version and firecracker_version when provided. The workflow also supports workflow_dispatch, weekly schedule, and reads the GitOps repository's omni/versions.yaml. The credential used to create the GitOps PR is named TALOS_GITOPS_DISPATCH_TOKEN; its token type is not specified in this repository.
Plain explanation. The source file contains the desired versions. The dispatch carries the two inputs that the build workflow accepts. The build produces installer tags and an OCI image. The workflow then writes the ledger and opens or updates the GitOps pull request. The Unraid repository is not written by that workflow.

Artifact invariants

  • Standard images never include the libvirt-only QEMU guest agent.
  • Unraid always selects the -libvirt image.
  • OCI always selects the standard image and OCI artifact.
  • Image tags and generated file content are produced by the build workflow; the ledger records the resulting schematic and OCI image identifiers.

Automation invariants

  • `versions.yaml` is the only human release input.
  • Unraid automation is not yet present; the current hand-off is an explicit CLI version.
  • Branches and PRs are idempotent per release request.
  • The build workflow creates or updates the GitOps PR; it does not update omni-on-unraid.
Plain explanation. The rules keep the two consumers from receiving the wrong image. OCI uses the standard installer and OCI artifact. Unraid uses the libvirt installer and provider setting. The checker compares the files that matter, so a version mismatch fails as a visible error instead of becoming a partial update.
One-line mental model: the Argo repository owns the desired version; the image repository owns artifact production; each platform repository owns its projection of the same artifact set.
